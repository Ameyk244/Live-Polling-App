# Concepts Applied — Live Polling App

Concept-to-implementation map for this project, with real file+line citations pulled
directly from the code as it exists today. Meant as a reference for explaining what was
built and why, not a tutorial — see `CLAUDE.md` for the original spec these were built
against.

## Socket.IO concepts

| Concept | File(s) + line reference | How it's applied |
|---|---|---|
| Rooms (one per poll code) | `app/sockets/events.py:45` (`join_poll`), `:78` (`join_as_host`); `app/services/poll_service.py:70` (`room=poll.code` on close broadcast) | The room name is literally the poll's `code` column — host and participants land in the same room by joining with that string. |
| Rooms as server-side authority | `app/sockets/events.py:40-45` (poll looked up server-side from `payload.poll_code`, not asserted); `:104,108` (`submit_answer` uses `claims.poll_id` from the verified token, never a client-sent poll id) | Room/poll identity always comes from a DB row or verified token, never a bare client claim of "I'm in room X." |
| Emit / On (bidirectional) | `@sio.on(...)` at `events.py:31,66,95`; `sio.emit(...)` at `events.py:56,116,124,128` and `poll_service.py:70` | Client→server via `on` handlers, server→client/room via `emit` calls. |
| Acknowledgements | `events.py:48-54` (`join_poll` return value), `:80-83` (`join_as_host`), `:122` (`submit_answer` returns `{"status": "ok"}`) | python-socketio delivers a handler's return value to the caller's ack callback automatically — no extra plumbing needed. |
| Error handling via emit (sender only) | `events.py:55-56, 84-85, 123-124` — every error path is `await sio.emit("error", {...}, to=sid)` | `to=sid` targets only the connection that triggered the failure; no error path in this file ever broadcasts to a room. |
| Connection-time middleware/auth | **Not actually implemented this way** — there is no `@sio.event` `connect` handler anywhere in `app/sockets/__init__.py` (3 lines total) or `events.py`. Auth happens per-event instead: `events.py:104` (`auth_service.authorize_participant`), `:75`→`poll_service.py:88`→`security.py:49` (`verify_host_token`) | Flagged as a real deviation below — see summary. |
| Never trust incoming socket events (payload validation) | `events.py:36,71,100` — `Payload.model_validate(raw_payload)`, wrapped to raise `ValidationError` on failure (`:37-38` etc.); schemas at `app/schemas/participant.py:4-10`, `app/schemas/answer.py:4-6` | Every socket payload is parsed through a Pydantic model before any business logic sees it — same discipline as REST bodies. |
| Delivery guarantees (at-most-once, no retry) | `events.py:113-120` | Comment explains python-socketio has no `volatile` flag at all (that's JS-client-only); there's no retry/backoff anywhere in this call — delivery is whatever the underlying WebSocket/polling transport gives you, once, best-effort. |
| REST + Socket.IO coexistence | REST: all of `app/routes/polls.py`. Sockets: all of `app/sockets/events.py` | Split follows `CLAUDE.md:25-28` — REST for create/fetch/host-action (one-shot, resource-shaped), sockets for anything that needs a live room (join, answer, broadcast). |
| DB as source of truth vs. socket as notification layer | `app/services/answer_service.py:38` (DB write via `answer_repository.create_answer`) happens *before* `app/sockets/events.py:116` (the `tally_update` broadcast); same order in `poll_service.py:67` (DB write) then `:70` (broadcast) | Write-then-notify every time — the socket emit never carries state the DB hasn't already committed. |

## Backend-from-first-principles concepts

| Concept | File(s) + line reference | How it's applied |
|---|---|---|
| Layered architecture — REST example | `routes/polls.py:18-23` (`create_poll` route) → `schemas/poll.py:26-36` (`CreatePollRequest`, validated by FastAPI's own body binding) → `services/poll_service.py:30-35` (`create_poll` service) → `repositories/poll_repository.py:10-18` (`create_poll` repository — the only place touching `db.add`/`db.commit`) | One full request trace across all four layers. |
| Layered architecture — socket example | `sockets/events.py:95-122` (`submit_answer` handler) → `schemas/answer.py:4-6` (`SubmitAnswerPayload`) → `services/answer_service.py:20-52` (business rules) → `repositories/answer_repository.py:24-37` (`create_answer`) | Same four-layer shape, mirrored for a socket event instead of a route. |
| Request/event validation | Routes: FastAPI binds `body: CreatePollRequest` automatically (`routes/polls.py:19`). Sockets: explicit `model_validate` calls (`events.py:36,71,100`) since raw socket payloads arrive as plain dicts FastAPI never sees. |
| Authentication vs. authorization | Authentication (issue/verify identity): `security.py:22-28` (`create_host_token`), `:31-39` (`create_participant_token`), `:42-46` (`_decode`, signature+expiry check). Authorization (permission decision): `poll_service.py:61` (`authorize_host(host_token, expected_poll_id=poll.id)` gating `close_poll`), `events.py:104` (`authorize_participant` gating `submit_answer`). |
| Stateless JWT-based auth | No session/token table in `app/models/` (only `poll`, `poll_option`, `participant`, `answer`); identity lives entirely in the JWT payload (`security.py:11-19`) | Zero server-held session state between requests — matches `CLAUDE.md:12`. |
| Middleware concept | REST side: `routes/polls.py:15,42` — `HTTPBearer()` dependency extracts/validates the bearer credential before the handler body runs, functioning as real per-request middleware. Socket side: see the "connection-time middleware" row above — deviates from that pattern (per-event, not per-connection). |
| Centralized error handling | `core/exceptions.py:5-46` (the `AppError` hierarchy: `ValidationError`, `UnauthorizedError`, `NotFoundError`, `PollClosedError`, `AlreadyAnsweredError`, `InvalidOptionError`, `RateLimitedError`), `:49-57` (`app_error_handler` + `register_exception_handlers`, wired once at `main.py:18`); the exact same exception types are caught again in every socket handler (`events.py:55-61, 84-90, 123-129`) and mapped to the identical `{code, message}` emit shape. |
| RESTful resource design | `routes/polls.py`: `POST /polls` (create), `GET /polls/{code}` (read), `GET /polls/{code}/results` (read, sub-resource), `POST /polls/{code}/close` (state-changing action, modeled as POST since "close" isn't a plain field replace). Status codes come straight from the exception hierarchy: 404/401/409/422/429 (`core/exceptions.py:14-46`). |
| DB schema + migrations | Models: `models/poll.py:9-25`, `poll_option.py:7-16`, `participant.py:9-20`, `answer.py:9-23`. Migration: `alembic/versions/fc2e34e3b8ab_create_initial_tables.py:24-61` (autogenerated from those models). FKs: `poll_options.poll_id`, `participants.poll_id`, and all three of `answers.{poll_id,participant_id,option_id}` (`answer.py:14-16`) each point back to their parent table, so an answer literally cannot reference a poll/participant/option that doesn't exist. Unique constraints: `polls.code` (`poll.py:13`) prevents two polls sharing a join code; `answers(poll_id, participant_id)` (`answer.py:11`) is the actual DB-enforced "one answer per participant" rule — see the race-condition row below for why the app-level check alone wasn't enough. |
| Parameterized queries / ORM usage | Every query in `repositories/*.py` goes through SQLAlchemy's `select(...)`/`db.execute`/`db.add`/`db.get` (e.g. `poll_repository.py:22-27`, `answer_repository.py:11-14,41-47`) | No raw SQL string concatenation anywhere in `app/`; the only literal SQL in the codebase is the static, parameterless `text("SELECT 1")` health-check probe at `routes/health.py:18`. |
| Rate limiting | `core/rate_limiter.py:9-13` (`check_submit_cooldown`, in-memory `_last_submit_at` dict keyed by `participant_id`) called from `answer_service.py:36` before persisting; `:16-17` (`record_submit`) called after, at `answer_service.py:39` | Protects `submit_answer` specifically from rapid repeat submissions per participant — in-process only, not distributed (by design, see out-of-scope section). |
| Environment/config validation on startup | `config.py:15-22` (`load_settings` catches any `Settings()` construction failure and re-raises as a `RuntimeError` with a clear message); `:25` runs it at import time | `main.py:8`'s import of `app.config` is what actually triggers the fail-loud check — missing `DATABASE_URL`/`JWT_SECRET` crashes the app before it can serve a single request. |
| Structured logging | `logging_config.py:5-16` (`configure_logging`; one formatter: timestamp/level/logger/message), wired once at `main.py:15`. Call sites: `poll_service.py:34` (poll created), `poll_service.py:81-83` (participant joined, inside `join_poll`), `answer_service.py:40-45` (answer submitted), `poll_service.py:68` (poll closed). |
| JWT hygiene | Algorithm pinned via `settings.JWT_ALGORITHM` (`config.py:9`, default `"HS256"`, never read from the token itself), passed explicitly to both `jwt.encode` (`security.py:28,39`) and `jwt.decode(..., algorithms=[settings.JWT_ALGORITHM])` (`security.py:44`) — decode only ever accepts that one algorithm, so a token can't downgrade itself to `"none"`. Expiry: `"exp"` claim set at `security.py:26,36-37` from `HOST_TOKEN_EXPIRE_HOURS`/`PARTICIPANT_TOKEN_EXPIRE_HOURS` (`config.py:10-11`). Signature: verified implicitly inside `jwt.decode` against the server's own `JWT_SECRET` (`security.py:44`); a forged/tampered token raises `jwt.PyJWTError`, caught at `:45-46` and turned into `UnauthorizedError`. |
| Authorization at point of access | `poll_service.py:59-65` (`close_poll`) — the host-only check (`authorize_host` + explicit `poll_id` match + open-status check) runs inside the function itself, immediately before the state change at `:67` — every call re-verifies regardless of how the caller got there, not just "some earlier gate was passed." |
| Race-condition handling | `answer_repository.py:24-37` (`create_answer` wraps `db.commit()` in `try/except IntegrityError`, translating a concurrent-duplicate DB violation into `AlreadyAnsweredError`); `events.py:125-129` (catch-all `except Exception` added to every socket handler) so an unexpected failure still emits to the sender instead of leaving the client hanging forever | Added during the security review — the original code only checked `has_answered()` in the service layer (`answer_service.py:33-34`), which is TOCTOU-vulnerable on its own; the DB unique constraint + `IntegrityError` catch is the actual guarantee. |
| Testing discipline | `tests/test_validation.py:7-25` — proves a 422 on bad input never reaches the service/DB (asserts `poll_count == 0` afterward). `tests/test_auth.py:1-41` — proves host-only close rejects a missing token and a valid-but-foreign-poll token, and only the correct token flips status to closed. `tests/test_socket_flow.py:6-36` — proves the full `join_poll` → `submit_answer` → `tally_update` loop round-trips over a real Socket.IO connection against a real live test server, nothing mocked. |

## Explicitly out of scope or not implemented

| Item | Reason |
|---|---|
| Volatile events | `python-socketio`'s Python server has no `volatile` emit parameter at all (it's a JS-client-only concept) — see `events.py:113-115`. Functionally moot here since `tally_update` never requests an ack anyway. |
| Connection state recovery | Not implemented — a disconnect/reconnect gets a fresh `sid` with no automatic re-sync of missed events. |
| Namespaces beyond default | Everything runs on Socket.IO's default `/` namespace (`sockets/__init__.py:3`); no per-role or per-feature namespace split. |
| Caching layers | Explicit in `CLAUDE.md:84-87`; every read goes straight to SQLite through the repository layer. |
| Horizontal scaling / Redis adapter | Explicit in `CLAUDE.md:84-87`; the rate limiter (`core/rate_limiter.py`) and the Socket.IO server both hold in-process state, so this only works correctly as a single instance. |
| Reverse proxy / TLS | Not configured — the app runs plain HTTP directly via uvicorn; left to whatever environment eventually deploys it. |
| Complex RBAC | Explicit in `CLAUDE.md:84-87`; only two flat roles exist (`host`/`participant`), no permission matrix. |
